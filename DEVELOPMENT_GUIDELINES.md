# Engineering guidelines

Этот документ фиксирует договорённости по разработке SPA грузовых аукционов.
Его цель — сохранить код понятным, проверяемым и предсказуемым по мере развития
проекта.

## Общие принципы

- Код должен объяснять себя через небольшие функции, ясные имена и узкие
  обязанности модулей. Комментарии нужны для объяснения причин и ограничений,
  а не для пересказа кода.
- Не допускаются неявные `any`, небезопасные type assertions и дублирование
  бизнес-правил между UI, API-клиентом и MSW-моками.
- Публичные модели и границы приложения (URL, HTTP, формы, localStorage)
  валидируются во время выполнения. Типы TypeScript не заменяют runtime-
  валидацию.
- Сначала создаются чистые функции и модели данных, затем адаптеры API и только
  после этого UI. Так правила проще тестировать и переиспользовать.
- Каждый React-компонент размещается в файле с суффиксом
  `*.component.tsx`, как требует задание.

## Архитектура: Feature-Sliced Design

- Используем слои `app`, `pages`, `widgets`, `features`, `entities`, `shared`.
  Направление импортов — только вниз по слоям; слой не зависит от вышестоящих.
- Внутри слайса придерживаемся сегментов по необходимости: `ui`, `model`,
  `api`, `lib`, `config`. Не создаём пустые директории заранее.
- `shared` содержит только переиспользуемые, предметно-независимые части.
  Правила аукционов находятся в `entities/auction` или соответствующей feature.
- Каждый слайс раскрывает наружу минимальный публичный API через `index.ts`.
  Внутренние файлы другого слайса импортировать нельзя.

## React и TypeScript

- Компоненты делают только представление и пользовательское взаимодействие;
  загрузка данных, преобразования и бизнес-правила выносятся в hooks, model или
  lib.
- Предпочитаем композицию небольших компонентов. Один компонент отвечает за
  одну заметную часть интерфейса или сценарий.
- Props описываем явными типами. Состояние выводим из данных там, где это
  возможно, вместо хранения его копии в `useState`.
- Имена собственных type aliases начинаем с `T`, а интерфейсов — с `I`.
  Типы сторонних библиотек и обязательные ambient-объявления не переименовываем.
- Для неизменяемых моделей, DTO и входных параметров чистых функций используем
  `readonly`-поля и `readonly T[]`, если изменение значения не является частью
  контракта.
- Обрабатываем состояния loading, error, empty и success. Не скрываем ошибку
  загрузки пустым экраном или пустым массивом.
- Используем доступные нативные элементы и семантику: `button` для действий,
  `label` для полей, видимый focus и понятные текстовые ошибки.

## Vite

- Vite используется только как слой сборки и локальной разработки; конфигурация
  остаётся минимальной и типизированной.
- Переменные окружения доступны только с префиксом `VITE_`; секреты не попадают
  в клиентский код и не коммитятся.
- Псевдонимы путей, если нужны, синхронизируются в `vite.config.ts` и
  `tsconfig.json`.

## UI: Tailwind CSS и shadcn/ui

- Базой стилизации служит Tailwind CSS. Токены цвета, типографики, отступов и
  радиусов определяются централизованно, а не копируются по компонентам.
- Для типовых интерактивных элементов используем `shadcn/ui`. Код добавленных
  компонентов хранится в репозитории и может осознанно адаптироваться под
  дизайн проекта.
- Компоненты `shadcn/ui` не заменяют проектные UI-компоненты: карточка
  аукциона, строка ставки и фильтр остаются собственными компонентами FSD.
- Tailwind-классы группируем в читаемом порядке: layout → spacing → typography
  → colors/visuals → states → responsive. Повторяющиеся наборы классов
  выносим в компонент или variant, а не копируем.
- Для уведомлений используем Sonner; иконки — `lucide-react`. Состояние формы
  остаётся в React Hook Form, а не внутри библиотечных компонентов.

## TanStack Router

- Роуты отражают пользовательские сценарии: список, детали аукциона, ставки и
  режим установки ставки по прямой ссылке.
- Все path params и search params описываются и валидируются через Zod. Для
  некорректных параметров задаются безопасные fallback-значения.
- Фильтры и пагинация — часть URL, чтобы экран можно было открыть, обновить и
  передать без потери контекста.
- Навигация выполняется типобезопасными API роутера, без ручной конкатенации
  URL-строк.

## TanStack Query

- Серверное состояние хранится в Query, а не в React state или MobX.
- Для каждого ресурса определяем централизованные, стабильные query keys и
  функции получения данных. Ключ включает все параметры, влияющие на ответ.
- Запросы имеют явные loading/error/empty-состояния. Детали аукциона
  префетчатся по intent/hover карточки списка.
- После успешной установки ставки инвалидируются query списка, деталей и
  истории ставок соответствующего аукциона.
- Не маскируем ошибки повторными бесконтрольными запросами; стратегия retry
  осознанно настраивается для ожидаемых ошибок API.

## Zod и React Hook Form

- Zod обязателен на всех границах, которые можно валидировать: search params,
  path params при необходимости, payload API, ответы API, данные localStorage,
  формы и конфигурация окружения.
- Из схем Zod выводим TypeScript-типы через `z.infer`; не поддерживаем вручную
  дублирующие интерфейсы.
- Схемы API точно выражают optional, nullable и enum-поля из OpenAPI. Любое
  преобразование DTO в UI-модель происходит после успешного `parse`/`safeParse`.
- Формы используют `zodResolver`. Схема ставки проверяет обязательность цены,
  значение больше нуля, а также динамические min/max/step из деталей аукциона.
- Ошибки валидации отображаются рядом с соответствующим полем. Ответ 422
  преобразуется в понятную ошибку формы или toast без потери информации API.

## MobX

- MobX применяется только для небольшого клиентского UI-state: например,
  состояние панели фильтров, локальные предпочтения отображения или toast-очередь.
  Серверные данные, кэш и мутации остаются в TanStack Query.
- Store имеет узкую ответственность, минимальный публичный API и не знает о
  React-компонентах. Побочные эффекты выполняются в явных actions.
- Состояние меняется только через actions; вычисляемые значения оформляются как
  `computed`. Не дублируем вычисляемое состояние в observable-полях.
- Компоненты-наблюдатели (`observer`) оборачиваются как можно ближе к месту
  чтения observable-данных, чтобы не расширять область перерендера.
- Данные, сохраняемые в localStorage, валидируются Zod-схемой при чтении и
  имеют безопасное значение по умолчанию.

## MSW и контракт API

- OpenAPI-схема — единственный источник правды для URL, методов, DTO, enum и
  ошибок. До создания моков контракт изучается и отражается в Zod-схемах.
- MSW использует in-memory store, поэтому успешная ставка обновляет текущую
  цену, пользовательский торговый статус и историю ставок. Следующий GET
  возвращает уже изменённое состояние.
- Моки воспроизводят ожидаемые сценарии: успешные ответы, 404, 422, пустой
  список, скрытую историю ставок и ограничения из detail DTO.
- Обработчики не должны возвращать произвольные упрощённые объекты, не
  соответствующие контракту.

## Тесты и проверка

- Не стремимся покрывать тестами каждую небольшую правку. Нужные, но отложенные
  сценарии фиксируем в `TEST_PLAN.md`.
- Автотесты обязательны для внешних границ и критичных бизнес-правил: Zod-контрактов,
  mutation ставки, `min`/`max`/`step`, 422 и регрессий. Тест проверяет поведение,
  а не внутреннюю реализацию.
- Для небольших изолированных изменений запускаем только релевантные проверки;
  полный набор typecheck, lint, test и production build выполняем перед вехой,
  интеграционным изменением или по запросу пользователя.

## Коммиты

- Агент не выполняет `git add` и `git commit`. После готового изменения он сообщает
  рекомендуемое название и состав атомарного коммита; коммит создаёт пользователь.
- История состоит из маленьких, логически завершённых и собираемых коммитов.
  Один коммит меняет одну связанную часть поведения, без смешивания рефакторинга
  и новой функциональности.
- Порядок работы: инфраструктура и контракт → модели/чистая логика → API и MSW
  → queries/router → UI → тесты и документация. Если зависимости требуют иной
  порядок, коммит должен оставаться понятным сам по себе.
- Сообщения коммитов пишем в повелительном наклонении и отражаем результат,
  например: `feat(auctions): add validated list filters` или
  `test(bet): cover bid step validation`.
- Перед коммитом проверяем, что в diff нет случайных файлов, форматирование
  единообразно, а проект проходит релевантные проверки.
- Не переписываем чужие изменения и не объединяем несвязанные правки ради
  удобства одной ветки.

## Правило принятия решений

Если возникает выбор между более коротким кодом и более очевидным кодом,
предпочитаем очевидный — при условии, что он не нарушает производительность или
архитектурные границы. Новая абстракция появляется только после второго
обоснованного повторения, а не на опережение.
